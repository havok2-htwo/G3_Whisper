# Changelog

Dieses Dokument wird bewusst knapp gehalten und bei kuenftigen Arbeiten fortgeschrieben.

## 2026-06-02

- **Neu:** Startup-Warmup: Das konfigurierte ASR-Modell wird beim Start eager geladen und mit `testaudio/Testaudio_02.wav` aufgewaermt (statt lazy beim ersten Request); danach wird der CUDA-Cache getrimmt, sodass die erste echte Anfrage warm ist. Best-effort: Ein Warmup-Fehler blockiert den Start nie.
- **Neu:** Idle-VRAM-Trim: Der Batch-Worker gibt den reservierten CUDA-Pool jetzt frei, sobald die Queue nach einem Burst leerlaeuft (nicht pro Batch -> kein Churn unter Last), sodass das Leerlauf-VRAM auf den Modell-Floor faellt und Platz fuer andere GPU-Tenants bleibt.
- **Neu:** `start.bat` setzt vor dem Start `PYTORCH_CUDA_ALLOC_CONF=garbage_collection_threshold:0.8,max_split_size_mb:256` (weniger Fragmentierung des reservierten Pools; `expandable_segments` wird auf Windows ignoriert).
- **Neu:** Experimentelle Precision-Option `fp8` -> `FineGrainedFP8Config` mit bf16-Compute, gated auf das importierbare HF-Paket `kernels` (sonst Fallback auf bf16, geloggt). Das `kernels`-Paket wird bewusst nicht automatisch installiert.
- **Fix:** fp16-`masked_fill`-Guard: Skalar-Maskenwerte, die fp16 uebersteigen (z.B. das hartcodierte `-1e9` im Cohere-ASR-Modell), werden auf die `finfo`-Grenze der Tensor-dtype geklemmt. Damit laeuft `int8_bnb` (fp16-Compute) ohne den `c10::Half`-Overflow-Crash; in-range-Werte sowie fp32/bf16 bleiben unveraendert. `bf16` bleibt am robustesten, `int8_bnb` spart am meisten Gewichts-VRAM.

Die Device-Auswahl zeigt Index, Name und Speichergroesse, z. B. `GPU 0 (NVIDIA GeForce RTX 3090, 24 GB)`.
- **RAM (Start-Umgebung):** `start.bat` setzt vor dem Python-Start `MIMALLOC_PURGE_DELAY=0` und `OPENBLAS_NUM_THREADS=4`. Der in torch (Windows) gebuendelte mimalloc behielt die freigegebenen CPU-Kopien aus dem Modell-Laden (MMS_FA in fp32 aus `bundle.get_model()`, Cohere vor `.to(cuda)`) dauerhaft committed (~4 GB Commit, bis ~2,4 GB echtes RAM, kein Leak, aber nie zurueckgegeben); mit Purge-Delay 0 gibt er sie sofort an Windows zurueck (Repro: Arena-Commit 0,985 -> 0,003 GB, Latenz unveraendert). numpy/scipy-OpenBLAS startet beim Import einen Thread pro Kern mit je 32 MiB nie beruehrtem Puffer (~1,5 GB Commit, 0 RAM); 4 Threads reichen, Laufzeit gemessen gleich. Bewusst `OPENBLAS_NUM_THREADS`, nicht `OMP_NUM_THREADS` (das wuerde auch die torch-CPU-Threads drosseln). `start.sh` und das Dockerfile setzen `OPENBLAS_NUM_THREADS=4` ebenfalls (mimalloc betrifft nur torch unter Windows).
- **VRAM (ReDimNet-Batch-Buckets):** ReDimNet fuellt CUDA-Batches nicht mehr pauschal auf 16 auf, sondern auf die naechste Zweierpotenz bis `REDIMNET_MAX_BATCH_SIZE = 8` (1/2/4/8; mehr Fenster laufen in 8er-Bloecken). Der Warmup bereitet alle vier Buckets vor (groesste zuerst, ~4 s je Form, Start ~8 s laenger), die OOM-Halbierung bleibt. Der reservierte Pool nach dem Warmup sinkt von ~5,6 auf 2,8 GiB. Embeddings unveraendert (Cosine 1,000000 gegen den alten Server fuer 1-, 5- und 20-Fenster-Stimmvektoren, pro Fenster >= 0,999998 gegen Batch 1). Mediane (RTX 4090, geteilt): 1/2/5/16/64 Fenster = 38/37/46/78/343 ms; Bulk-Durchsatz ~10 % unter Batch 16. Die 192D-Verifikation nutzt jetzt denselben Default statt fest `batch_size=16`.
- **VRAM (MMS_FA in FP16):** Das Alignment-Modell liegt auf CUDA in FP16 (`MMS_CUDA_DTYPE`), Emissions werden fuer den CTC-Aligner nach FP32 gecastet. Resident 1,2 -> 0,6 GB, Peak 1,77 -> 1,21 GB, Alignment der 10-min-Referenz 1,9 -> 1,3 s. Gegen FP32: alle 1297 Woerter, Reihenfolge, Sprecherzuordnung und 146 Saetze identisch; Abweichung im Mittel 0,06 ms, max. 20 ms (ein Emission-Frame, 5 Woerter). BF16 war ungenauer (max. 80 ms) und wird nicht verwendet.
- **Performance (Cohere CUDA-Graphs, `cohere_cuda_graphs`, default an):** Neues Modul `backend/genesis_whisper_server_cohere_cuda_graphs.py` ersetzt fuer Cohere auf CUDA (fp16/bf16) `model.generate` durch einen statischen Greedy-Decoder (Cross-K/V einmal pro Request, Prompt eager, jeder Token-Schritt ein Graph-Replay pro Batch-Bucket 1/2/4/8/16) und `model.encoder.forward` durch Graph-Replays ueber 128-Frame-Buckets bis 35 s (Batch-Buckets 1/2/4). Gemessen ueber `process_local_asr_batch` auf dem GPU-Executor (RTX 4090, geteilt): 2-s-Clip 269 -> 30 ms, 14,4-s-Datei 905 -> 116 ms, Mixed-Batch 3 915 -> 170 ms, 20 Zufallsclips 17-24 s -> 2,2 s; Transkripte byte-identisch (opt-in GPU-Test `tests/test_cohere_cuda_graphs_gpu.py` mit `G3_GPU_TESTS=1`). Sampling/Beams/unbekannte kwargs, > 16 Zeilen, > 35 s, CPU sowie int8_bnb/fp8/fp32 laufen unveraendert eager.
- **VRAM (CUDA-Graphs):** Warmup beim Modell-Load (Decoder B=1/2/4, Encoder B=1 alle 28 Frame-Buckets, groesste zuerst) kostet ~5 s und ~550 MB; weitere Buckets capturen lazy. Harte Obergrenzen: max. 89 Graphen und 1536 MB Graph-Speicher (statische Puffer + private Pools), darueber bleibt die Form eager. Gemessener Worst Case mit allen erlaubten Buckets: 1,32 GB. Zwei Funde aus der Produktivsetzung: (1) lazy in aufsteigender Laenge gecapturte Encoder-Graphen liessen den gemeinsamen Pool auf 7,4 GB wachsen -> jeder Batch-Bucket captured jetzt zuerst seine groesste Form; (2) ein neuer Side-Stream pro Install leakte je ~9 MB cuBLAS-Workspace und der Default-Capture-Stream pinnte den ersten Graph-Pool -> ein prozessweiter Side-Stream fuer Warmup und Capture. Graph-Speicher ueberlebt den Idle-Trim und wird beim Entladen/Neuladen freigegeben (`_cleanup_previous_model` deinstalliert vor `empty_cache`).
- **Thread-Regel:** Install und Warmup laufen in `load_local_asr_model` und damit im Server immer auf dem GPU-Executor-Thread (Startup-Warmup, Admin-Reload, Lazy-Load im Batch-Worker); nur dieser Thread darf spaeter capturen, andere Threads spielen vorhandene Graphen ab und rechnen fehlende Formen eager.

- **Neu (fairer ASR-Scheduler):** Der Batch-Worker plant Batches jetzt nach dem Vorbild der OmniVoice-Queue: Jeder Request ist ein Job mit eigener Chunk-Liste, Batches werden **round-robin** ueber die aktiven Jobs (gleicher Processing-Key) zusammengesetzt, bediente Jobs rotieren ans Ende (LRU). Ein Ein-Satz-Live-Request landet damit im naechsten Batch statt hinter dem 32er-Fenster eines 2-h-Jobs; der **First-Chunk-Fast-Path** (`scheduler_first_chunk_fast_path`, default an) gibt ihm sogar einen eigenen Mini-Batch, wobei Fast-Path- und Regelbatches alternieren, damit der lange Job nicht verhungert. Lange Jobs (>= `scheduler_long_job_min_chunks`, default 5) belegen einen von `scheduler_max_parallel_long_jobs` Slots (default 2, 0 = unbegrenzt), weitere warten FIFO; kurze Jobs warten nie. `batch_wait_time_ms` haelt einen Batch nur noch zurueck, wenn ein frischer Job da ist. Das bisherige Enqueue-Fenster (`2 * batch_max_segments`) entfaellt.
- **Neu (lange Cohere-Audio als Superchunks):** Im `transcript`-/Legacy-Pfad ging eine lange Aufnahme bisher als **ein** Queue-Item an Cohere (das intern chunkt) — ein einziger GPU-Lock-Hold ueber die gesamte Transkription, den kein Scheduler unterbrechen kann. Audio ueber 60 s wird jetzt wie im WXC-Pfad per Silero in ~25-s-Superchunks (±250 ms Padding) zerlegt; kuerzere Aufnahmen bleiben unveraendert ein Item (kein VAD-Lauf, keine Naehte).
- **Fix (Decode blockierte den ganzen Server):** Ein WAV/FLAC-Upload mit abweichender Samplerate wurde bisher per libsamplerate (`sinc_best`, pybind11) in einem Aufruf resampelt, der die GIL fuer die gesamte Dauer haelt — bei einer 1-h-Datei ~33 s, in denen der Event-Loop und damit **jeder** Live-Request stehen blieb (gemessen: Live-Requests warteten bis zum Ende des Decodes). Resampling laeuft jetzt ueber ffmpeg im eigenen Prozess (1-h-Datei: 1,5 s statt 33 s); ohne ffmpeg greift ein Streaming-Fallback mit 200-ms-Chunks, dessen Ausgabe bit-identisch zum bisherigen One-Shot-Aufruf ist. 16-kHz-Uploads bleiben unveraendert auf dem SoundFile-Pfad.
- **Messung (1-h-WAV als Bulk-Job, parallel alle 2 s ein 6-s-Live-Request, Cohere fp16 auf RTX 5090):** vorher Live-Median 14,2 s / p95 22,2 s / max 51 s (jeder Live-Request wartete auf den kompletten Bulk-Job); nachher Median 1,9 s / p95 2,8 s / max 4,5 s bei Idle-Latenz ~0,6 s, Bulk-Job 53 s statt 54 s.
- **Default (`batch_max_audio_seconds` 300 -> 100):** Ein Cohere-Batch von 200-300 s Audio kostet ~2 s GPU-Zeit und einen entsprechend grossen Allokator-Pool; ein Live-Request wartet je Lock-Phase auf genau diesen Batch. Auf einer 24-GB-Karte mit DIA/Embed/OmniVoice als Mitnutzern lief der Whisper-Prozess mit 200-s-Batches waehrend eines Diarisierungs-Bulk-Jobs auf 17 GB dedicated + 2,3 GB via WDDM ausgelagert, wodurch ReDimNet ~100x langsamer wurde (Verification 321 s statt 5 s, Embeddings 11 s statt 0,1 s, bis zum Neustart). 100 s halbiert Live-Wartezeit und Batch-VRAM bei minimalem Durchsatzverlust.
- **Neu (GPU-Phasen in Scheiben):** Speaker-Clouds, MMS-Alignment und die 192D-Verifikation eines Diarisierungs-Jobs hielten `local_gpu_lock` bisher am Stueck (gemessen bei 47 min: Alignment 23 s, Verifikation bis 321 s) — solange kam kein Live-Request an die GPU. Die drei Phasen sind jetzt in CPU-Plan, GPU-Scheibe und CPU-Finish geteilt (`plan_speaker_windows`/`build_speaker_clouds`, `alignment_bounds`/`align_chunk_slice`, `plan_verification_windows`/`finish_verification`); `run_sliced_gpu_phase` haelt den Lock nur je Scheibe (64 ReDimNet-Fenster bzw. 4 Alignment-Chunks, unter einer Sekunde) und gibt ihn dazwischen an wartende Batches/Embeddings ab. Ergebnisse sind identisch zu den Ein-Aufruf-Varianten, die fuer Tests/Tools erhalten bleiben.
- **Default (`cuda_memory_trim_after_batch` -> `true`, Idle-Frist 250 ms -> 5 s):** Auf einer geteilten 24-GB-Karte muss der Leerlauf-Footprint nahe am Modell-Floor bleiben (siehe Paging-Befund oben). Der Trim greift erst nach 5 s leerer Queue, damit stetiger Live-Verkehr den warmen Pool behaelt; die Re-Reservierung kostet gemessen ~80 ms einmalig (ReDimNet-Batch 16: 176 ms statt 86-139 ms).
- **Admin:** `GET /api/admin/queue` liefert `jobs` (aktiv/wartend mit Fortschritt und Queue-Wartezeit), `recent_jobs` sowie pro Batch `unique_request_count`/`fast_path`; die Admin-UI zeigt Scheduler-Settings, aktive/wartende Jobs und die Job-Historie. Der Admin-Benchmark reicht jede Wiederholung als eigenen Job ein und misst damit das reale Scheduling.
- **Fix (WXC-Wiederholungsfilter):** ASR-Wiederholungsschleifen (z. B. ein "So. So. So."-Loop aus einem Cohere-Decode auf schwierigem Audio) werden im WXC-Diarisierungspfad jetzt pro Chunk **vor** dem Alignment gefiltert. Bisher lief der Repetition-Filter erst pro Satz — und weil das Satz-Splitting an "." einen solchen Loop in viele Einzelwort-Saetze zerlegt, sah der Per-Satz-Filter nie eine Wiederholung. Auf der 10-min-Referenz kollabierte dadurch ein 94-faches "So." auf ein einziges (echtes) Vorkommen und die Segmentzahl fiel von 250 auf 156. Der Per-Satz-Filter bleibt zusaetzlich als Sicherheitsnetz erhalten; `X-G3-Repetition-Filter: off` schaltet beides ab.
- **Fix (Known-Speaker-Matching gegen unreine Cluster):** Ein enrollter Sprecher wird jetzt auch identifiziert, wenn seine frisch erkannte DIA-Wolke `low_support` oder `mixed_cluster` ist — vorausgesetzt die Evidenz ist ueberwaeltigend (Cosine >= 0,75 UND Support >= 0,80). Bisher verlangte jede gueltige Zuordnungskante `status == "ready"`, sodass ein bekannter Sprecher mit unreiner Wolke selbst bei ~0,99 Cosine und vollem Support faelschlich als `unresolved` zurueckkam (typisch fuer Sprecher mit Overlap/Code-Switching). Schwache Matches bleiben unveraendert `unresolved`. Der Support wird pro Cluster-Fenster gemessen, ein echter Zwei-Personen-Blend kann die 0,80-Schwelle daher nicht ueberschreiten; das Hungarian-Stabilitaetskriterium gilt weiterhin. Der Cluster-Status bleibt in `speaker_assignments[].embedding_status` erhalten und ein zusaetzliches `KNOWN_SPEAKER_IMPERFECT_CLUSTER`-Warning macht die Audio-Qualitaets-Einschraenkung sichtbar.
- **Neu (v2 `language`-Parameter):** Das v2-Request-JSON akzeptiert optional ein Top-Level-`language` (z. B. `"de"`, `"en"`, `"auto"`; Werte wie in den Admin-Optionen).
